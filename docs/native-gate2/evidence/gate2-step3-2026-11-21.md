## 1. The bug — root cause (proven)

The guest’s `FSE_readNCount` stored each 16-bit normalized count at a **1-byte stride instead of a 2-byte stride** — the recompiler dropped the `LSL #1` scale on the STRH address.

- Location: `F:\SplatNative\build\gen\main_gen_055.c`, `fn_ca26e1c` (FSE_readNCount), **line 164859** — the ONLY `st16` in the whole readNCount region (lines 164365–165064).
- Original: `st16(c, (c->x[28] + (uint32_t)c->x[27]), (uint16_t)((uint32_t)c->x[9]));` where x28 = normalizedCounter base, x27 = charnum (element index, incremented by 1).
- Proof: the correct shorts `[10, 14, 3, 2, 1, -1, 0, 0, -1]` stored as overlapping STRH at `nc + charnum` reproduce the guest memory bytes `[0A, 0E, 03, 02, 01, FF, 00, 00, FF, FF]` exactly, which read back as shorts give `[3594, 515, -255, 0, -1, 0, 0, 0, 0]` — the corrupt dump. The bitstream decode itself was correct (tableLog 5, maxSV 8, count values right — only their placement was wrong). The old "frequencies sum to 4109" was the sum of the POSITIVE corrupt counts (3594+515); the raw sum was 3853.

## 2. The fix

Changed the store to scale the index by 2, with an explanatory comment:

```c
st16(c, (c->x[28] + 2 * (uint32_t)c->x[27]), (uint16_t)((uint32_t)c->x[9]));
```

- File/line: `F:\SplatNative\build\gen\main_gen_055.c:164863` (after the comment). Applied via `/tmp/s17_edit4.py`’s predecessor `/tmp/s17_edit3.py` (anchor-asserted, applied OK).
- Other unscaled `st16(c, (base + (uint32_t)index),...)` patterns exist elsewhere in main_gen_055.c (lines 208359+, 231903+, 242054+, 403701+, 509870+) — different functions outside the zstd path; NOT touched (out of scope; the verification run will reveal if any of them matter).
- No repo writes, no pushes. Local tree only. `main.c` still withheld (builder name).
