## The §17 blocker, restated
- Guest stops at the heap-def load: heap-name global `0xe6f3b88` is never written, so the

- With the name seeded, the `.zs` heap-def decompression runs but returns an error and the
  loader aborts on the unfilled buffer.

## Root cause (found 2026-11-21)
The `.zs` decompression fails with **`ZSTD_error_srcSize_wrong` (-20)** — NOT because the
arguments are wrong (they are all verified correct, see below), but because the guest’s
static libzstd builds a **corrupt FSE decoding table**:

- The FSE table build (`fn_ca27160`, `FSE_buildDTable`) spreads symbol occurrences into a
  **4096-entry (12-bit) table** with step `2563 = (4096>>1)+(4096>>3)+3` and mask `4095`.
- The bigtrace shows the spread step `fn_ca27240` executing **4109 times** — i.e. the
  normalized frequencies the guest read sum to **4109, not 4096** (overcount of **13**).
  A valid stream’s frequencies must sum to exactly the table size (a power of 2); 4109 is
  not a power of 2, so the frequency data the guest decoded is wrong.
- After 4109 placements the spread position is
  `(4109 × 2563) mod 4096 = 551`, not `0`.
  (Verified: 4096 placements → position `0`; 4109 → `551`.)
- The next function `fn_ca27274` (Huffman table build) checks `if (x14 == 0)` on entry and
  returns **`-1`** when it is not — so it returns `-1` because `x14 = 551`.
- The caller maps that failure to **`-20` (`ZSTD_error_srcSize_wrong`)** via `fn_ca2254c`
  (`x0 = 0xFFFFFFFFFFFFFFEC`, then epilogue `fn_ca22550`).
- The loader ignores the error, BYML-checks the unfilled buffer (`0x9016e270`), fails,
  and aborts via `nn::diag::Abort`.

So the `-20` is a **symptom of a corrupt FSE table**, not a wrong `srcSize`. The fault lies
upstream of the `-20`, in how the normalized frequencies are decoded (`FSE_readNCount`
bitstream) or in the table-build inputs — the next fix must target that, NOT the call
arguments.

## What was verified correct (do NOT re-derive)
- **The file is valid.** `F:\Splatoon Games\System\HeapSize\Product.HeapDef.byml.zs`
  (1222 bytes, zstd magic `28 B5 2F FD`) decompresses with real zstd (Python `zstandard`
  0.25.0, installed via pip on the PC) to **2604 bytes** of valid BYML
  (`59 42 07 00 …` = "YB", version 7). Frame header declares content size 2604;
  frame = 7-byte header + 3-byte block header + 1212-byte block = 1222 bytes exactly.
- **Loader → decompression wrapper call is correct.** Mark on `0xca219c0`
  (run `boot_20261121_144738.log:8129`):
  `x0=20ffed60 (struct) x1=abd001c0 (src) x2=4c6 (1222, correct srcSize) x3=0 x30=d191234`.
- **Block decompression call is correct.** Mark on `0xca22570`
  (run `boot_20261121_145410.log:8129`):
  `x0=abd006c0 (dctx) x1=9016e270 (dst = heap-def buffer) x2=a2c (2604, correct dstCapacity)
  x3=abd001ca (src = block data, file offset 10) x30=ca23328`.
  Block header `e5 25 00` → type 2 (compressed), size `(0x0025e5>>3) = 1212`; the
  `srcSize >= blockSize` check (`1215 >= 1212`) passes.
- **Header parse is correct.** `fn_ca219c0` validates the magic `0xfd2fb528`, parses the
  7-byte frame header (FCS flag 1 → 2-byte FCS = 2604), and re-enters itself with
  `srcSize=7` (header-only, hook run `boot_20261121_145155.log:8132`,
  `x0=abd07730 x1=abd001c0 x2=7 x3=0 x30=ca231d4`).
- **FSE table build runs and Huffman build is reached.** Bigtrace: `fn_ca27240`/`fn_ca27244`
  ×4109 each (the spread loop), `fn_ca2722c` ×7, `fn_ca27274` once, then `fn_ca2254c`
  (`-20`). `fn_ca27160` init confirmed: `x8 = 1<<tableLog` (4096), `x11 = 4095` (mask),
  `x12 = 4095` (threshold), `x15 = 2563` (step), `x14 = 0` at spread start.
- **The mark on `0xca26bd0` was a red herring** (it is an internal helper, not the
  top-level entry): `x0=20ffe650 x1=20ffe868 x2=20ffe86c x3=abd001cf (buffer+15)`.
  Do not use it as the decompression entry; the entries are `0xca219c0` (wrapper) and
  `0xca22570` (block).

   instead of 4096. Prime suspect: `FSE_readNCount` bitstream decoding (the frequencies
   are decoded from a compact bitstream before `FSE_buildDTable`), or the inputs passed

   the struct — requires vendoring a host zstd decompressor; the runtime currently has
   no zstd, only `src/runtime/vendor/lz4.c`.)

   writer** — the real fix for `0xe6f3b88` (the seed is only a diagnostic).
3. Then, in README order: step 2 NVN API surface, step 3 title/plaza draw + CSV in the
   same run (the Gate 2 pass bar).
